# Fresh Studio Kysely schema and migration workflow (#129–#130)

Kysely is the selected application schema and runtime persistence for both
SQLite and PostgreSQL. `pnpm --filter @noveltea/studio migrate` and
`migrate:kysely` use the same migration implementation. Web and Agent refuse
absent, stale, or incompatible schemas and never run migrations on startup.
The older Studio development database is incompatible and is not adopted.

## Explicit maintenance

In the Studio working directory, with the normal Better Auth OAuth
configuration supplied in `.env` or environment variables:

```sh
# SQLite (default). For an incompatible legacy database, manually back up/reset first.
pnpm --filter @noveltea/studio migrate:kysely up
pnpm --filter @noveltea/studio migrate:kysely check
pnpm --filter @noveltea/studio migrate:kysely down
```

For PostgreSQL, explicitly set `NT_STUDIO_DB_BACKEND=postgres` and
`PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`, `PGPASSWORD` to a dedicated
**empty** database with an authorized migration role; then run the same
`migrate:kysely up|check|down` command. `up` applies the pending application
migrations, `check` is a read-only fail-closed readiness check, and `down`
rolls back one application migration. Rolling back the baseline **deletes
application data** but preserves Better Auth-owned tables and users.
Do not target a legacy Studio database: untracked old tables are
rejected and there is no automatic data migration or adoption.

Better Auth runs its supported native Kysely migrations **before** the Studio
Kysely Migrator. The application baseline only references auth's `user`
table; `user`, `session`, `account`, `verification`, and `rateLimit`
are never created, dropped, or versioned by Studio migrations.

## Developer migration workflow (#130)

The default Compose initializer invokes `migrate`, which uses the same Kysely
migrator as `migrate:kysely`. These commands require a Kysely database or
an empty database, never an legacy application schema:

```sh
pnpm --filter @noveltea/studio migration:new add_example_column
pnpm --filter @noveltea/studio migrate:kysely up
pnpm --filter @noveltea/studio rollback-one
pnpm --filter @noveltea/studio migrate:to baseline
pnpm --filter @noveltea/studio migrate:to 0000_studio_baseline
pnpm --filter @noveltea/studio migrate:to none
pnpm --filter @noveltea/studio migrate:to latest
pnpm --filter @noveltea/studio typegen
pnpm --filter @noveltea/studio typegen:check
pnpm --filter @noveltea/studio migrate:kysely check
```

Scaffolding runs `kysely-ctl migrate:make` against an isolated in-memory
database and **creates a file**, not a schema diff. Author the migration's
`up(db)` and `down(db)` operations explicitly, using lowercase snake_case
filenames. Missing reverse operations and unedited up/down scaffold stubs are
rejected, never treated as successful no-ops. An irreversible migration should
explicitly throw in `down(db)`. Valid reverse migrations may discard data
introduced by `up` (Django-style semantics). Applied migration files are
immutable: missing, renamed, future, or out-of-order history fails closed.
The first baseline now also creates an application-owned `studio_migration_sources`
ledger, with SHA-256 checksums of the exact applied source (the baseline SQL
and its interpreter, or each authored migration file). The ledger is updated
inside each migration's transaction, including rollback; readiness refuses
missing, divergent, or modified source entries even if the resulting DDL is
unchanged. The ledger is excluded from `StudioDb` codegen and application
schema parity. **Existing early-development Kysely databases created before
this checksum ledger must be explicitly reset**; they are not silently adopted.
Better Auth's schema is independently owned; no legacy migration journal is adopted.

The canonical `web/src/db/studio-db.ts` is generated by `kysely-codegen`
from a **new temporary migrated SQLite database** on every invocation, with
`CamelCasePlugin` naming. Better Auth tables and migration journals are
excluded. `typegen:check` regenerates it and fails if committed output drifts.
Regenerate and commit this file when an authored schema migration changes it.

The physical database representation used in `StudioDb` is numeric INTEGER
(including 0/1 booleans and generated keys) and string TEXT (JSON and UTC
timestamps). `kysely-values.ts` offers strict conversions for boolean,
JSON, timestamps and PostgreSQL BIGINT strings / SQLite number values;
unsafe integers are rejected rather than silently narrowed.

## Schema parity

The immutable `web/kysely-schema/0000_studio_baseline.sql` asset is the
new application's ordered, logical migration source. It contains 33
application tables, indexed constraints, and 15 effective triggers from the
finalized existing schema. The dialect-specific DDL helpers in
`web/src/db/kysely-baseline.ts` handle only:

- PostgreSQL table/index creation and deferral of composite foreign keys
  until owner-pair unique indexes exist;
- integer identity generation rather than SQLite `AUTOINCREMENT`;
- PL/pgSQL trigger functions, including immutable identity guards,
  same-Story execution admission, derived Turns and steer-only execution
  associations;
- `NO ACTION DEFERRABLE INITIALLY DEFERRED` on PostgreSQL references
  where multi-branch cascading deletion can otherwise transiently violate
  an otherwise valid transaction. Cascades/SET NULL actions remain the same.

Per Gate 0, there are two deliberate extensions beyond the old application
schema: `thread_queued_message_edits.sequence` and
`thread_steering_checkpoint_links.sequence` are generated integer keys.
The original `request_id` and `(message_id, checkpoint_sha)` identities
remain uniquely indexed, and timestamps are unchanged. Consumers must order
by those sequence keys, not SQLite `rowid`, UUID, or a potentially tied
timestamp. A generated identity orders allocation, not commits across
uncoordinated writers; use the shared transaction guards when porting the
actual persistence operations.

The runtime checker does not automatically migrate, rebuild indexes,
repair data, or adopt a legacy migration journal. It inspects the Kysely history and
physical schema. SQLite verifies exact DDL (including triggers, CHECKs,
defaults, nullability, indexes) and FK integrity; PostgreSQL verifies
columns, PKs, owner-qualified FKs and delete actions, CHECK expressions,
indexes including partial predicates, and enabled trigger bodies. PostgreSQL's
expected tables, explicit indexes, and translated triggers are derived from
the _entire_ authored SQLite migration history, not only the baseline;
additional application-owned tables, indexes, CHECK/unique constraints or
triggers fail closed. Auth and
journal objects are excluded. Translating a new trigger requires the common
baseline-compatible SQLite trigger syntax and its matching PG trigger function
implementation; unsupported definitions fail inspection rather than being
silently ignored. Authentication
table creation/validation remains Better Auth's responsibility.

## Cross-engine certification

```sh
pnpm --filter @noveltea/studio typegen:check
pnpm --filter @noveltea/studio exec tsx --test test/kysely-schema.test.ts test/kysely-workflow.test.ts

# PostgreSQL tests run in independent per-test schemas of the database you select:
NT_TEST_PG_URL=postgresql://... pnpm --filter @noveltea/studio exec tsx --test test/kysely-schema.test.ts test/kysely-workflow.test.ts
NT_TEST_PG_URL=postgresql://... pnpm --filter @noveltea/studio schema:parity
```

The PostgreSQL suites accept an explicit `NT_TEST_PG_URL` for any test
instance; they do not assume or configure a local PostgreSQL setup. Each run
creates and cleans up only its own uniquely named schema. Parity migrates a
separate in-memory SQLite database, compares application columns, logical
types, generated identities, nullability and defaults, then validates the
constraints, foreign keys, indexes and triggers. It also tests real driver
output for booleans, JSON, timestamps and BIGINT. CI provisions PostgreSQL 17
and runs both backends, code generation, and parity as required gates.

The suite uses the same assertions on both engines: two upward migrations,
Kysely rollback/reapply, Better Auth user creation, composite ownership,
CHECK and uniqueness, immutable ancestry, event/queue ordering, derived
Turn associations, cascade effects, and read-only schema-drift rejection.
It also rejects untracked legacy application tables and incompatible/future migration
histories without modifying them. The Studio application regression suite exercises the shared Kysely runtime;
legacy database tests and adapters are retired by the #141 cutover. The
migration and readiness boundaries are documented in `docs/kysely-cutover.md`.

# Kysely Gate 0: SQLite/PostgreSQL transaction and portability audit

Status: **PASS WITH BINDING IMPLEMENTATION CONDITIONS** for architecture feasibility; **not** PostgreSQL implementation or certification.
Issue: [#126](https://github.com/Cruel/noveltea-gen/issues/126) · Parent: [#125](https://github.com/Cruel/noveltea-gen/issues/125) · ADR: [0001](adr/0001-kysely-sqlite-first-studio-persistence.md).
Audited checkout: `5091d85` on `main`; 2026-11-09. This is a read-only code audit plus disposable, isolated transaction prototypes; no domain SQL has been converted.

## Decision and bounds

**One shared implementation of each Studio persistence algorithm is feasible with a small semantic transaction/lock layer and dialect-specific DDL/value/connection code.** No reviewed operation intrinsically requires a second PostgreSQL domain repository. This is a **feasibility assessment**, not a proof of PostgreSQL runtime parity: #128 must establish the production transaction primitive under real PostgreSQL contention and #142 must prove full cross-engine concurrency. If either reveals an invariant that cannot be enforced by narrow backend helpers, **stop and reopen the architectural decision** rather than duplicate domain code.

Three cross-cutting correctness hazards must be addressed up front:

1. **Connection escape/nested transactions.** A majority of the current `db.transaction(() => ...)` callbacks call captured root `db` and synchronous helpers rather than the transaction parameter. This works because Drizzle/better-sqlite3 runs on the same SQLite connection. With a pooled PostgreSQL root, these calls execute **outside** the transaction and can observe inconsistent state, deadlock themselves, or survive rollback. The shared port must pass one typed transaction-scoped executor through *all* nested helpers. In particular, **continuation → enqueueGeneration / protected decision / steering / message seeding / assistant settlement** must compose in the caller's transaction and never independently start a root transaction.
2. **Implicit SQLite-wide writer serialization.** `BEGIN IMMEDIATE` on a single SQLite database file effectively serializes all writers, and even the ordinary autocommit statements take writer locks. PostgreSQL READ COMMITTED plus separately committed statements does **not** protect read-check-write sequences. Acquire the guard as the **first statement of the transaction, before reading preconditions**, and keep precondition, CAS, inserts, trigger effects and transition inside it. The simplest safe escape hatch is one transaction-scoped PostgreSQL **global write advisory lock** for **every mutating Studio operation**, including currently autocommit CAS/INSERT/UPDATE/DELETE calls, until narrower guards are proven by the tests. Otherwise an unguarded writer could bypass the advisory lock and invalidate the precondition of a guarded operation; the global lock would **not** emulate SQLite serialization. This conservative fallback is intentionally throughput-limiting, but keeps one algorithm. Do not silently trade correctness for parallelism; narrower Thread/Job guards or lock-free single-statement CAS may replace it only when **all interacting writers** have proven compatible locking/constraints and the same cross-process tests pass.
3. **Triggers, allocation order and external/auth schema.** SQLite triggers currently enforce immutable identities, checkpoint parent/receipt validity and automatically create Story Turns/Turn→execution associations. Their PostgreSQL equivalents need carefully authored integrity DDL or a single shared write implementation plus DB-level protection; dropping them would weaken the domain. SQLite `rowid` does not exist on PostgreSQL; generated integer identity values order allocation, not necessarily commit visibility. Better Auth's physical `account.userId`/`account.providerId` names differ from application snake_case and must not be accidentally rewritten by `CamelCasePlugin`.

The audit found **48 explicit persistence transaction invocations in 11 SQLite domain files**, plus important unwrapped compare-and-swap/atomic statement operations, schema triggers, SQLite schema introspection, the auth storage binding, raw read-only controller access, and DB fixture adapters. The inventory below is exact for the inspected revision. An implementation agent should re-run the inventory after code churn, not treat line numbers as stable.

### Proposed minimal semantics

Retain one owner-scoped, asynchronous `StudioStore` facade. Persistence modules share `Kysely<StudioDb>` queries, receive an explicit transaction-scoped `Transaction<StudioDb>`/query executor, and use one backend-owned wrapper around operations:

- `withWriteTransaction(scope, fn(tx))`: atomic callback, guaranteed rollback on exception, guard acquired **before** any predicate reads. `scope` is a *semantic key*, not a dialect switch; preliminary needs are `exclusive` (safe fallback), `queue`, `thread(threadId)`, `job(jobId)`, and (if proven necessary) `identity(id)` for as-yet-uncreated rows. Do **not** build arbitrary nested transactions as an application feature. For nested operations, pass the existing `tx` to a shared internal function and do not call `withWriteTransaction` again.
- `query executor` passed to pure query helpers is either the root Kysely executor for a standalone read or the current `tx` for transactional work. All domain helper functions should be query-executor-parametric; do not close over the root `db` in a transaction callback.
- SQLite implementation: immediate-write transaction via **Kysely driver begin override** (or equivalent verified transaction owner, not a raw `BEGIN` accidentally executed on a different connection). PostgreSQL implementation: transaction-scoped `pg_advisory_xact_lock` for the global queue/transition scope, plus `SELECT FOR UPDATE` on existing Thread/Job parents (or transaction advisory locks keyed on absent identities) where supported by *every* interacting writer. No multi-statement model/Git/network I/O while locks are held.
- Lock acquisition order: acquire a global queue/exclusive guard first when required, then Thread identity, then Job/child identity, then child rows, using deterministic key sorting for multiple Threads/Jobs. A narrower writer must **not** bypass a global guard on a shared invariant. PostgreSQL transaction retry policy should handle `40P01` deadlock and `40001` serialization failure with bounded whole-transaction retries; distinguish semantic conflicts/uniqueness violations from transient failures. SQLite lock-busy retry must also be bounded; avoid retrying external side effects.
- Keep single-statement CAS, unique constraints, owner-filtered `UPDATE ... WHERE ... RETURNING`, conditional `UPSERT`, and `INSERT ... ON CONFLICT DO NOTHING` as **shared** Kysely operations where sufficient. Pure reads do not need writer locks. A standalone CAS is exempt from a *fine-grained* guard only when its interaction with guarded transactions is proven safe; under the temporary **global-serialization fallback** all mutating operations must participate, with targeted relaxations introduced only after proof.

**Guard legend in the inventory:** `Q` = global queue capacity/writer-admission guard; `T` = Thread identity/sequence/lineage guard; `J` = Job or active Pi execution guard; `I` = stable identity/Story/child reservation guard, including nonexistent rows; `G` = global bounded reconciliation (or global exclusive fallback); `C` = guarded conditional statement / DB uniqueness (no multi-statement lock beyond the containing transaction). These are *requirements of the shared operation*, not six obligatorily different backend helper implementations; `exclusive` may initially implement combinations safely. Every line's proof should run against both backends through the **same** public persistence port.

### Dialect-sensitive SQL and schema requirements

- **`rowid` (exact four uses):** `thread-message-sqlite.ts:262` orders edit history; `:352` retrieves the earliest old body used for idempotent enqueue replay. `steering-sqlite.ts:334` retrieves the newest verified implementation link, and `:352-354` the latest pending unresolved link. Both tables currently use noninteger primary keys: queued edit `request_id` TEXT PK, checkpoint link composite `(message_id,checkpoint_sha)` PK. A durable generated identity/sequence is warranted in **both tables** because first/latest insertion order, not necessarily user-supplied timestamps, has semantic meaning. Keep request-id/composite uniqueness, `edited_at`/`recorded_at`, and enforce a same-message/Thread writer guard if visibility ordering matters. Existing `generation_run_queue.sequence` and `generation_events.id` are already generated integer IDs; **do not add replacements** without a demonstrated requirement.
- **Portable query fragments:** `COALESCE`, `CASE WHEN`, `EXISTS/NOT EXISTS`, `COUNT`, `MAX`, `LOWER`, conditional `UPDATE`, `INSERT ... ON CONFLICT`, `RETURNING` and ordered SELECTs have usable SQLite/PostgreSQL equivalents in shared Kysely. Re-express Drizzle raw SQL via Kysely expressions while preserving parameters and aliases; don't mechanically copy SQLite-qualified identifiers. `COUNT(*)` and some integer/boolean/JSON values differ at runtime; normalize them at the backend boundary.
- **Trigger parity:** The baseline schema has immutable Thread/run/Turn identity, checkpoint fork/restart proof, same-owner Story/run registration, anti-deletion guards, and four Turn/Turn-execution derivation events. The later migration changes the live-steering trigger to **steer-only** and makes the new Turn inherit the message's pinned creative policy. PostgreSQL migrations must reproduce this **final effective behavior**, including `INSERT OR IGNORE` → `ON CONFLICT DO NOTHING`, SQLite `RAISE(ABORT)`/null-safe `IS NOT` → appropriate PostgreSQL trigger function/condition, and an explicit no-overwrite invariant. DDL may differ per dialect; **do not fork the domain persistence algorithm**. If maintaining business-effect triggers in two dialects violates the agreed zero-duplication threshold, move derived Turn/association writes to one shared transactional implementation but retain equivalent DB-enforced identity/provenance protections. Run exact trigger-behavior tests on both engines before acceptance.
- **Schema ownership and naming:** The Better Auth `account` table has mixed-case physical `userId` and `providerId` columns read by Git identity/rebinding logic. An app-wide `CamelCasePlugin` otherwise translates them to `user_id` and `provider_id` and breaks access. Keep Better Auth's adapter/migrations independent; use a narrow auth-owned projection, quoted raw identifiers (parameterized inputs), or an explicit connection/query boundary that bypasses app-style name transformation. Preserve Better Auth-first table/foreign-key migration ordering.
- **SQLite-specific introspection:** Existing readiness checks rely on `sqlite_master`, PRAGMAs, SQLite DDL text and `foreign_key_check`. PostgreSQL needs dialect-native catalog introspection and integrity equivalents; this is backend infrastructure, not domain repository duplication.
- **Identity and value representation:** Map SQLite `INTEGER PRIMARY KEY AUTOINCREMENT` and booleans stored as integer to explicit PostgreSQL identity and boolean conventions; normalize large `COUNT` values, timestamps/text and JSON before they enter a common TypeScript contract. Retain unique `(threadId,sequence)`, run-order and partial one-preparing constraints and all owner-scoped composite FKs. Foreign-key and trigger comparison must test semantics, not assume verbatim DDL text parity.
- **Untrusted/controller data:** SQLite read-only controller currently selects the trusted Job's owner, provider, repository ID, directory, pin and config. PostgreSQL uses a restricted role and controller-only Compose network with the *same typed query*; never expose full application DB access or auth secrets.

## Proof of Kysely 0.29.7 SQLite immediate-lock support

Environment: Node 24.18.0; project-installed `kysely@0.29.7`, `better-sqlite3@12.11.1`; two independent handles to a disposable temporary SQLite file in WAL mode. No project or developer database was touched.

1. **Observed upstream default:** inspected installed Kysely `SqliteDriver.beginTransaction`: it executes `CompiledQuery.raw('begin')`, **not** `BEGIN IMMEDIATE`. Merely invoking `db.transaction().execute` would weaken the existing writer-admission invariant.
2. **Scoped-connection prototype:** `db.connection().execute(async connection => { BEGIN IMMEDIATE; INSERT; COMMIT; })` acquired the writer lock. Second handle's INSERT returned `SQLITE_BUSY`; after commit it could insert. Observed: `immediate started true`, `second writer failure SQLITE_BUSY`, committed count 1, post-commit count 2.
3. **Transaction-wrapper prototype:** a disposable `SqliteDialect` driver wrapper overrode `beginTransaction` to issue `CompiledQuery.raw('BEGIN IMMEDIATE')` on the **same acquired connection**, delegating all other driver methods unchanged. `db.transaction().execute(async tx => ...)` blocked second writer (`SQLITE_BUSY`), automatically rolled back on an intentionally thrown exception (remaining rows **0**), and committed a later transaction (rows **1**). This shows normal Kysely transaction lifecycle and rollback can be preserved without copying domain operations. The prototype used a temporary in-memory JS wrapper only; production code must implement/test its typed form in #128.
4. No PostgreSQL service was invoked during this audit. PostgreSQL lock equivalence is an explicitly **unverified** implementation/certification gate, not claimed as a passed test here.

## PostgreSQL feasibility addendum after #127 (2026-11-09)

#127 introduced a real PostgreSQL 17-alpine server, scoped application/controller roles, and isolated rootless Compose test infrastructure. This addendum extends Gate 0's *native PostgreSQL concurrency evidence* without claiming a migrated Studio store. Unlike the initial SQLite-only driver proof, the new certificate uses multiple independent PostgreSQL TCP sessions authenticated as the **application role** against a fresh per-run PostgreSQL Compose project and uniquely named database volume. It starts only PostgreSQL, never Studio or Pi, and deletes only its own volume.

Run from the repository root:

`pnpm certify:postgres-transactions`

Implementation: [`scripts/certify-postgres-transactions.ts`](../scripts/certify-postgres-transactions.ts). The certificate asserts rootless Docker before startup and uses `compose.yaml`, `compose.postgres.yaml`, and `compose.postgres.test.yaml` to avoid loading developer service environment files. It checks three prerequisites directly against PostgreSQL:

1. **Transaction-scoped advisory-lock contention:** With one transaction holding `pg_advisory_xact_lock`, another independent session sees `pg_try_advisory_xact_lock = false`. After rollback **and after commit**, the second session can acquire the lock. This proves the primitive's lifetime but not the eventual Kysely wrapper's correct use of it.
2. **Transaction connection and rollback visibility:** A writer transaction reads its own uncommitted row, while a second connection observes zero rows. Rolling back leaves zero persisted rows. Every nested Kysely helper in #128 must receive the same transactional executor; the test demonstrates why root/pool connections cannot substitute for it.
3. **One-slot queue admission with two clients:** Two sequential claim attempts compete while the first holds the advisory transaction lock; the second waits, observes the committed first claim, and cannot overclaim capacity. The initial claimant takes the oldest of two queued jobs, and after both transactions one job remains queued. This validates the basic locking strategy, **not** all real Studio queue/FIFO state-machine behavior.

These are deterministic, credential-free **database primitive** tests. They do not add a PostgreSQL Studio schema, duplicate domain repository, PG application driver, or model/provider integration. They are a prerequisite to #128's shared helper work, **not a replacement** for its implementation tests or #142's multi-process certification. In particular the certificate does not prove that unguarded autocommit writes in the future Studio code participate in the same lock, nor that the real queue helper takes the guard before every precondition read.

**Still mandatory for #128 and later:** produce the typed `Kysely<StudioDb>` implementation; test global guard participation by every interacting write; real PG transaction-scoped nested helper isolation/rollback; bounded retries/deadlock order (`40P01` and `40001`); lock release after connection termination; absent-row reservation races; and generated event-ID allocation/commit-order cursor races. Run these with a real PostgreSQL server and competing connections, then repeat relevant behavior through the same StudioStore tests on both dialects. Failure requiring domain-repository duplication reopens the architecture gate.

## Gate 0 review decision

**Architecture gate: PASS (feasible, conditional on required proofs).** There is no identified domain operation that must be implemented twice. The simplest safe design is a common Kysely query algorithm with a transaction-scoped executor and an initially conservative writer lock; fine-grained locks can be introduced only after the same tests establish equivalence. Material correctness work remains in #128/#129 and later tests. **Stop** if those prototypes/tests reveal that a shared algorithm cannot preserve any invariant without substantial duplicated business logic. This report records the feasibility pass and the precise follow-up criteria; it does **not** certify PostgreSQL or authorize bypassing the blocking dependencies.
